scenarios:
  - id: "s1-okr-writing"
    category: "ambiguous-requirements"
    scenario_title: "你的 leader 让你写双月 OKR，你列了一堆『完成 XX 需求』，leader 说『这是 task 不是 objective』，而你不确定一个合格的 O 该长什么样。"
    junior_approach: "把需求清单直接当 OKR 交上去；或者写一堆『提升体验、保证稳定』这类不可衡量的口号，落不了地也验不了收。"
    senior_approach: "把任务翻译成可衡量的结果（如『把导出功能的使用率从 X 提到 Y』『把接口 P99 从 X 降到 Y』），定一个有挑战的 O 配可验证的 KR，显式标注挑战项与保底项。"
    trade_offs: "选择写有挑战的目标——意味着可能完不成、拿不满；但轻松完成的 OKR 既说明目标定低了，也让你的成长停滞。"
    senior_steps:
      - move: "把『完成 X 需求』改写为『X 带来的结果』，用使用率、延迟、成本等可量化指标表达。"
        rationale: "OKR 的 O 是结果不是动作；翻译的过程逼你先想清楚这个需求到底为什么有价值。"
      - move: "定一个有挑战的 O + 2-3 个可验证的 KR，标注哪些是保底、哪些是挑战。"
        rationale: "挑战项是拉伸空间，保底项是安全网；分开标注让评估时既不冒进也不保守。"
      - move: "与 leader 对齐结果口径与验收方式，确认『做到什么算达成』。"
        rationale: "验收口径前置，双月结束时能自证达成与否，而不是靠叙述。"
    trade_off_details:
      - choose: "有挑战的结果型 OKR"
        over: "保守的任务清单"
        cost: "可能完不成挑战项、评分打折；换成长速度与对目标的真正理解"
  - id: "s2-cross-team"
    category: "cross-team-conflict"
    scenario_title: "你的功能需要另一个团队改一个接口字段，对方说这季度没排期，而你的双月目标卡在这里，催了两次对方都在忙自己的 OKR。"
    junior_approach: "反复催促或在群里抱怨『不配合』，把协作问题升级成情绪问题；或者绕过对方自己 hack 一个临时方案，埋下兼容隐患。"
    senior_approach: "带着完整上下文（你的目标、对方改动的真实成本、对齐后的共同收益）找对方同学，先理解对方的 OKR 与约束。提出最小改动方案（对方只需加一个可选字段），并主动承担联调。必要时借 leader 协调但自己全程跟进。"
    trade_offs: "选择主动承担额外的联调工作——代价是自己多花时间，换来对方的配合意愿与长期协作关系。"
    senior_steps:
      - move: "先理解对方：对方这季度在冲什么、改这个字段对他们的真实成本是多少。"
        rationale: "跨团队的第一现场是信息不对称；理解对方约束后，诉求才可能被听见。"
      - move: "把诉求压缩成最小改动（如加一个可选字段而非重构接口），并主动承担联调与测试。"
        rationale: "把对方的成本降到最低、把配合的门槛降到最低，是执行层跨团队拉通的唯一杠杆。"
      - move: "借 leader 的协调但自己全程跟进，不让协调变成甩锅。"
        rationale: "leader 是放大器不是替身；跟进到底才能建立自己的跨团队信用。"
    trade_off_details:
      - choose: "最小改动 + 主动承担联调"
        over: "催促施压或私自 hack"
        cost: "自己多花时间做非本职的联调；换协作顺畅与长期关系"
  - id: "s3-speed-quality"
    category: "incident"
    scenario_title: "业务催得紧，你压缩了测试时间上线一个改动，结果一个小 bug 引发线上问题被叫停，leader 复盘时问『为什么没拦住』。"
    junior_approach: "归咎『时间太紧没办法』；或者从此每次都要测很久、层层加码，把迭代节奏拖到业务无法接受。"
    senior_approach: "先止损修复。复盘时把『时间紧』与『质量门缺失』分开。真正的问题是缺一个最低限度的发布检查（核心路径单测 + 灰度）。把这次教训固化成自己的发布 checklist。"
    trade_offs: "选择建立最低质量门——代价是每次发布多花一点时间，但相比一次线上事故的代价，这是极划算的保险。"
    senior_steps:
      - move: "先止损：快速修复回滚，恢复优先于追责。"
        rationale: "事故现场的第一原则是恢复；归因放到止血之后。"
      - move: "复盘区分两个变量：时间压力是客观约束，质量门缺失才是可控漏洞。"
        rationale: "把失败归因到可控项才能改进；归因到『时间紧』等于什么都改不了。"
      - move: "建立自己的最低发布 checklist（核心路径单测 + 灰度 + 回滚预案），急需求也不跳过。"
        rationale: "速度与质量不是对立的；一个轻量的底线让『快』可持续。"
    trade_off_details:
      - choose: "最低质量门 + 急需求不破例"
        over: "为速度跳过验证或层层加码测试"
        cost: "每次发布多花少量时间；换线上事故风险的大幅下降"

anti_patterns:
  - name: "Task 思维"
    manifestation: "把 OKR 当任务清单，完成动作即算达成，不看业务/技术结果。"
    why_it_fails: "字节考核看结果不看过程；task 思维会让人停在执行层，失去成长与晋升空间。"
    correction: "每个目标写成可衡量的结果，标注『达成意味着什么』，用结果而非动作自评。"
  - name: "等指令"
    manifestation: "什么事都等 leader 安排，不敢自己定优先级或主动要上下文。"
    why_it_fails: "Context not Control 的文化把判断权下放给你；等指令等于主动放弃这个空间，也辜负了扁平文化。"
    correction: "主动要上下文、主动提方案，带着判断去沟通而非带着问题去上交。"
  - name: "唯快不破的误读"
    manifestation: "把『追求极致』理解成越快越好，跳过测试与数据验证，靠返工补质量。"
    why_it_fails: "字节的快建立在数据验证与质量之上；盲目快会以返工、事故的形式加倍偿还，反而更慢。"
    correction: "快的同时守住最低质量门与数据验证，把『快』做成可持续的。"

## 专家按语

字节 2-1 与阿里 P6 是同一执行层的两种文化切片。阿里靠『评审闸门 + 稳定性纪律』托底。字节靠『上下文 + 结果导向』放权。前者的暗知识是克制与留痕。后者的暗知识是判断与结果。拿到上下文后敢不敢自己定优先级，是 2-1 分化的关键。能不能把『做完』翻译成『做到』，同样关键。

两者有共同地基：可靠交付、数据说话、留痕可追溯。无论范式与文化如何差异，执行层的可信度都建立在可被验证之上。建议与 `alibaba-p6-backend` 并读。再看 `tencent-hunyuan-ailab` 中执行层如何在 AI-Native 语境里被重新定义。
